## 1 — App key separation

Both keys were generated by the owner in the App settings UI, because there
is no REST endpoint for it. Each was then proven independently, from the
host that would use it, against readbacks rather than assumptions.

```text

K_edge     c7fe54edbae7929e  edge      6/6 PASS, proven from the edge itself
K0         5f559f7e1f30eb0b  still installed, NOT yet deleted
```

Each proof covers: private key readable · JWT accepted · `app.id == 4669438`
· installation `155393018` present · installation token minted · expected
repository accessible. Nothing is inferred from a previous step; a minted
token does not prove the repository is reachable, so both are checked.

`K_edge` was delivered over stdin and never existed as a separate file in a
readable location on the way. The downloaded copies were removed from the
Windows Downloads folder after installation — which reduces further
exposure without undoing the fact that the material passed through that
filesystem.

### A defect the rotation itself exposed

`openssl` is absent from `PATH` outside the flake devshell. It produced zero
bytes, and `sha256("")` is a perfectly stable value, so all three distinct
keys reported the same fingerprint:

```text
app        e3b0c44298fc1c14
K_primary  e3b0c44298fc1c14
K_edge     e3b0c44298fc1c14
```

A rotation cannot be verified by a constant. `fingerprint()` now refuses to
hash empty output and fails the whole verdict when it cannot derive a public
key.

### Outstanding

`K0` is still valid. Its deletion is a UI step, and it must come *after* both
runtimes are running on their own keys — which they now are. Until then,
`OLD_SHARED_KEY_REVOKED` cannot be claimed.

### What this is, restated

Rotation isolation, not permission isolation. Both keys carry the authority
of the same App, so an attacker holding the edge PEM before revocation holds
the App's repository permissions and bypasses `WatchdogCapability` entirely
— that class is a property of the edge *code*, not of the credential. What
is bought is precise: the edge credential can be killed without killing the
primary.

## 2 — Alerting

Channel: Telegram (`@review_governance_bot`) for Governor and edge
incidents; email via HetrixTools for off-host availability. Both leave the
primary and the edge.

### Payload is an allowlist

Fields outside `{severity, cause, repo, pr_number, check_run_id,
incident_id, detected_at, state}` raise rather than being stripped, and
causes must be preregistered. A redaction pass is a list of the leaks
somebody thought of; there is nowhere here to put a webhook body, an OAuth
token, provider content or a PEM.

### Alerts are transitions

A standing condition does not re-page every poll. A cleared one sends a
recovery. An undelivered alert is retried every poll, and an undelivered
*recovery* keeps the incident open — otherwise a channel outage would
silently close an incident nobody knows is still running.

### Proven end to end, twice, on a real condition

The synthetic drill passed first (`incident_delivered`,
`recovery_delivered`, condition closed). More usefully, a real outage:

```text
receiver stopped   2026-08-26T12:15:27Z
receiver started   2026-08-26T12:19:00Z
outside view       HTTP 502 via Caddy throughout

12:15:29Z  WARNING   webhook_receiver_unavailable  delivered   +2 s
12:15:39Z  CRITICAL  watchdog_not_polling          delivered  +12 s
12:19:03Z  RECOVERY  webhook_receiver_unavailable  delivered
12:19:13Z  RECOVERY  watchdog_not_polling          delivered
open afterwards: none
```

### The defect this row exists to catch

The **first** attempt delivered nothing to anyone. The monitor was
configured correctly, the contact list was bound to it, the downtime was
detected from three locations and recorded, and the uptime report was
accurate — and the recipient address carried a transposition typo
(`kcousrce` for `kcsource`), so every alert went to a stranger's mailbox.

Everything green, nobody told. That is exactly why this row demanded
delivery to a human instead of a successful `curl`, and it is the same
failure shape the whole program exists to refuse. It was found by reading
the account through the HetrixTools API rather than by another round of
screenshots; contact lists are read-only there, so the fix was the owner's,
in the UI.

### Two more defects found while wiring this

**`delivery_stuck` could never clear.** Nothing ever advanced
`processing_state` on the edge, so the warning would light once and stay
lit, which is how an alert class gets ignored. The primary now POSTs an
authenticated, monotone `/signals/ack` after its cursor advances. It is
advisory in the strict sense: the primary's cursor remains the only
authority, reconciliation ignores both, and `DROPPED` rows are never
touched so the A5a-c2 reconciliation fixture stays visible.

**The sentinel paged on its own startup.** At 10:27:38Z it raised
`reconciliation_stale` simply because it started before the first sweep
landed, and recovered 22 s later. Every restart of the stack would wake the
operator for nothing, and an operator woken by routine restarts stops
reading the alerts that matter. Fixed with a startup grace that applies to
`NOT_REPORTED` only — the *absence* of data. A timestamp that exists and is
old is a real condition and still pages immediately, at startup like any
other time.

### A compromise recorded rather than hidden

`watchdog_not_polling` and `webhook_receiver_unavailable` both fire for a
single root cause: two messages, one incident. Suppressing the first would
lose visibility of the watchdog for the entire duration of a receiver
outage, which is worse. Recorded for the owner to rule on.

### An honest gap

```text
user_authorization: NOT_REPORTED
```

`auth_lost` and `refresh_outcome_unknown` are **forwarded**, not detected.
The sentinel never probes a refresh token, because Device Flow refresh
tokens are single-use with rotation and probing one is a write that can
strand the credential. Nothing currently writes `auth-state.json` — the A1c
lifecycle code lives on its own branch — so those two CRITICAL causes are
wired to a silent producer. The sentinel renders this as `NOT_REPORTED`
rather than `HEALTHY`, because an unreported subsystem that shows green is
how a dashboard starts lying.

### A running watchdog is not a watching watchdog

Nothing paged if the watchdog stopped. `Restart=always` covers a crash but
not a hang, `systemctl is-active` is true for a loop that stopped looping,
and the off-host monitor watches the *receiver*. The independent failure
domain could have gone quiet with every dashboard green.

The watchdog now stamps every poll into the edge database, `/healthz`
exposes `last_watchdog_poll` and a counter, and the sentinel raises
`watchdog_not_polling` past 60 s — treating an unreachable edge as
`NOT_REPORTED` rather than as fine. This is one event beyond the
preregistered minimum list, added deliberately.

### Soak, counted rather than calculated

The first summary derived poll counts by dividing the window by the
interval. Elapsed time proves a poll was *due*, not that it happened. The
observer counts distinct observed values only.

```text
window          2026-08-26T10:35:35Z .. 10:38:36Z   (79 /healthz samples)

distinct heartbeats                 12   required >= 4
distinct reconciliation sweeps       6   required >= 2
distinct watchdog poll timestamps   19   required >= 2
watchdog poll counter delta         18
```
