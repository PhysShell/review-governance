# Governor operations runbook

Applies to the `ai-final-review` gate once A5b activates it. Written during
A5a, before activation, so that the procedures exist before they are needed
rather than being invented during the first incident.

## Two rollbacks that must never be confused

```text
SERVICE ROLLBACK
    deploy the previous Governor build
    the ruleset stays ACTIVE
    the gate stays fail-closed
    no approval beyond normal deployment is required

ENFORCEMENT BREAK-GLASS
    the owner explicitly disables or deletes the ruleset
    the merge gate OPENS
    an incident record is required
    NEVER automatic
```

A provider outage, a webhook outage, an OAuth loss or a rate limit is
**not** a reason to disable enforcement. Fail-closed that becomes
fail-open whenever it is inconvenient is not fail-closed; it is a delay.

## Break-glass procedure

Rehearsed in A5a (drill P3) against an isolated ruleset, canonical hash
verified identical before and after.

1. Record the incident and the reason. No verbal approvals.
2. Snapshot the ruleset JSON, store its id and canonical hash.
3. Explicitly disable (`enforcement: disabled`) or delete it.
4. Perform the exceptional operation — and only that one.
5. Restore the exact snapshot.
6. Verify by independent readback that the canonical hash is identical.
7. Record closure, including what was merged while the gate was open.

The canonical hash is generated by
`experiments/operational-readiness/harness/cutover.py ruleset`, so a
restore is checked against a computed object, not against somebody's
recollection of the settings page.

## Bypass policy

```text
CONFIGURED_BYPASS_ACTORS = NONE
```

Nobody is on the bypass list, including the Governor App itself. The
honest caveat, stated rather than hidden: the repository owner keeps
administrative authority and can disable or delete the ruleset. "No bypass
possible" would be false; "no bypass is configured, and removing the gate
is an auditable administrative act" is true.

## Authorization loss (A1c semantics)

```text
user auth lost / refresh outcome unknown
  -> no new provider triggers
  -> every standing SUCCESS invalidated
  -> installation identity projects failure
  -> human reauthorization required
  -> a fresh review round before any new success
```

Neither the primary nor the watchdog restores a success after
reauthorization. The reauthorization restores the *ability to review*, not
the *evidence*.

If **installation** authority is lost — as opposed to user authorization —
the Governor cannot even patch its own checks. That is an infrastructure
incident with its own alert: the gate stays as it was last projected, which
is why the Governor must never leave a success standing while it still has
the ability to revoke it (A3b-c3).

## Liveness and the watchdog

```text
primary heartbeat            every <= 15 s
watchdog declares stale      after <= 45 s of silence
outage -> successes revoked  <= 60 s target
                             A5a-c2 observed: 52 s, on the external host
                             (45 s stale window + 10 s poll + one round trip)
```

The 52 s is the measured number from the deployed configuration, not a
target. The earlier 35 s belongs to an in-host prototype and does not apply
to the external failure domain.

The watchdog runs in a separate runtime and failure domain, uses the
installation identity, and holds no user credentials. Its capability is
enforced in code: read state, and patch an existing Governor check run to a
non-passing conclusion. Nothing else.

**A running watchdog is not a watching watchdog.** `systemctl is-active` is
true for a loop that stopped looping, and `Restart=always` covers a crash
but not a hang. So the watchdog stamps every poll into the edge database and
`/healthz` exposes it:

```text
GET /healthz -> {"last_watchdog_poll": "...", "watchdog_polls": N}
```

The primary sentinel raises `watchdog_not_polling` (CRITICAL) when that
timestamp is older than 60 s, and treats an unreachable edge as
`NOT_REPORTED` rather than as fine. Nothing else covers this: the off-host
uptime monitor watches the *receiver*, not the watchdog.

**The watchdog must outlive its own incidents.** It is deployed with
`--window 0` and `Restart=always`, and never with `--stop-after-incident`.
A5a-c2 found it deployed as a bounded fixture: it exited cleanly after its
first revocation and stopped watching, with nothing in the service state to
say so. If you ever see `governor-watchdog.service` inactive with a
successful exit, that is not a completed job — that is the safety net folded
up and put away.

**A watchdog trip is not undone by the primary returning.** During the
outage nobody was watching the providers' mutable carriers, so a fresh
qualification is required. Any change that would auto-restore a revoked
success is a change to the safety model and needs the same scrutiny as
turning the gate off.

## Detection and reconciliation

```text
webhook ACK                                <= 2 s   (GitHub aborts at 10 s)
webhook event -> durable observation       P99 <= 10 s  (A5a-c2: 3.0 s)
reconciliation interval                    <= 30 s
observed invalidation -> failure CONFIRMED P99 <= 5 s   (A3b: ~1 s)
external mutation -> failure CONFIRMED     <= 60 s target
```

The healthy path is a pull, not a push: `signal_client` on the primary asks
the edge `GET /signals?after=<cursor>`, receives delivery **metadata only**,
and re-reads GitHub for every fact. The edge is never a second source of
truth, and the primary never accepts an inbound connection.

Reconciliation is part of the safety model, not a convenience: GitHub does
not automatically redeliver failed webhooks, so anything missed is only
ever found by reading. A2b demonstrated reconciliation discovering a head
change with **no** delivery at all.

**Reconciliation must never consult the cursor or the spool.** A5a-c2
demonstrated the point live: with two deliveries marked `DROPPED` and the
cursor deliberately left behind, reconciliation still found the drift, and
the cursor was identical before and after. If reconciliation is ever
"optimised" into skipping work the fast path has already covered, a delivery
that never arrived becomes invisible to the one mechanism meant to catch it.

The receiver contract (A2a): receive bytes → verify HMAC → validate event →
durably record the delivery GUID and payload metadata → **only then** ACK
2xx → process asynchronously. The GUID stays the idempotency key; GitHub
reuses it on redelivery, which A2a observed live.

## What a green check does and does not mean

Admissible:

> GitHub prevents merge whenever the latest-head Governor check, from the
> expected Governor App, is not in a passing state. The Governor fails
> closed for every invalidation it has observed, and a success does not
> outlive the runtime responsible for revoking it beyond the watchdog
> threshold.

Not admissible, and not provable while providers emit mutable advisory
comments:

> A PR can never be merged after its provider evidence becomes invalid.

## Operational notes discovered in A5a

- A required-status-check ruleset also blocks **direct pushes** to the
  protected ref, not only merges. Moving a protected branch requires a
  legitimate PR that satisfies the rule — which is desirable in production,
  but surprises anyone expecting to push a hotfix.
- Under `strict`, a merge blocked by base drift reports the same
  `"…is expected."` text as a merge blocked by a missing check. GitHub does
  not distinguish them, so the Governor's own surface must: an operator
  cannot tell "never reviewed" from "reviewed, branch behind" from the API
  error alone.
- Updating a PR branch produces a **new head with zero checks**, which is
  exactly the intended consequence: the previous review does not travel.
